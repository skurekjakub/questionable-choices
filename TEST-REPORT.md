# MVP QA run — questionable-choices

## Verdict

**PASS with gaps.** The MVP does what `docs/spec.md` says it does: the board is an exact
projection of the epic, sessions start, track state through hooks, survive a server restart,
and stop cleanly. Seven defects were found, none of them data-losing; four clauses could not
be exercised in this environment and are listed with their reasons. Every previously-recorded
"still does not work" item in `docs/verification.md` was re-checked: three are fixed, three
are still true and are by design.

Assumptions taken unattended, as the run had nobody to ask:

1. **Permission mode for the `waiting-permission` probes was `manual`, not `default`.** The
   requester's brief said "permission mode `default`", but `docs/verification.md` records
   that `default` passes no flag and therefore inherits the owner's `auto` setting, which
   never prompts. `manual` is the mode the README tells the owner to pick "if you want to
   answer every tool call from the board", so it is the one that exercises the clause.
2. **Probe prompts always replaced the prefilled one in full.** No session ever received the
   implement or test playbook prompt. Every probe forbade file writes, commands and posting,
   except two that named one specific `touch` of a file inside the scratch directory in order
   to raise a permission prompt. Every session's transcript was read afterwards to confirm it
   did only what the probe said. Nothing was written to Jira and nothing in either repository
   was modified by a session.
3. **`DOC-9999999` could not simulate a Jira failure.** Jira answers `200 {"issues":[]}` for a
   parent key that does not exist, so no error exists to show. A workspace with a
   deliberately invalid `jql` was added instead (via the API, since the dialog has no `jql`
   field) to produce a real Jira 400.
4. **The branch checked out in `docs-workspace` was not restored.** The brief forbids
   `checkout` in that repository. Its HEAD moved from `refactor-content-validate-on-engine`
   to `main` during the run; the reflog shows five clean round trips between the two, none of
   them attributable to the dashboard (`git grep checkout src/connectors/repos/git` is empty).
   The coordinator confirmed `main @ b10c92a386` as the baseline to restore to, and that is
   the state it is in.

## Bugs found

### 1. A dirty worktree can never be removed from the UI — the force affordance is unreachable

- **Symptom.** Removing a worktree with uncommitted changes is refused with the right message,
  but the "Remove anyway, discarding changes" button that spec §12 requires never appears, so
  the removal is a dead end in the UI. The same dead end catches a worktree whose directory was
  deleted by hand.
- **Repro.** Start a session, let it exit, write any untracked file into its worktree, open the
  session view or the issue drawer, click **Remove worktree**.
- **Expected.** The refusal, plus a force confirmation offering "Remove anyway, discarding
  changes" (spec §12; `docs/verification.md` § _What still does not work_ says the force
  confirmation "belongs on the dirty-tree refusal only").
- **Observed.** The refusal renders as `role=alert` with git's porcelain output; the button row
  stays `Open in VS Code · Remove worktree · Copy`. Clicking again just re-earns the 409.
- **Root cause.** `src/web/src/api.ts:285` — `isForceableRemoval` returns true only when the
  409's `detail` contains the literal `--force`. `src/connectors/repos/git/index.ts:63` —
  `DirtyWorktreeError` builds that detail as ```${path} has uncommitted changes; removing it
  needs force` `. The two strings never match, so `setForceRemove(isForceableRemoval(cause))`
  is always false and the branch at `SessionView.tsx:235` / `IssueDrawer.tsx:336` never renders.
- **Impact.** Both force paths are UI-unreachable. `POST /api/sessions/:id/remove-worktree`
  with `{"force":true}` works, so the fix is a string, not a mechanism. This is a functional
  regression against the change `docs/verification.md` proposed: the affordance moved off the
  live-session refusal (correct) but did not arrive on the dirty one.
- **Screenshots.** `evidence/21-live-refusal.png`, transcripts `evidence/21-remove-force.txt`,
  `evidence/21-remove-missing.txt`.

### 2. Closing a menu-launched overlay drops focus to `<body>`

- **Symptom.** Escape (or Cancel) on **Add workspace…** or on **Remove this workspace?** leaves
  `document.activeElement === document.body`. A keyboard user is dropped to the top of the
  document and has to tab back in.
- **Repro.** Keyboard only: focus the workspace button, Enter, ArrowDown to "Add workspace…",
  Enter, Escape. Then: focus the workspace button, Enter, End ("Remove this workspace"), Enter,
  Escape.
- **Expected.** Focus returns to the control that opened the overlay — the workspace switcher
  button — as it does for the start dialog and the issue drawer.
- **Observed.** `{"dialogs":0,"tag":"BODY","isBody":true}` in both cases.
- **Root cause.** `src/web/src/hooks/useFocusTrap.ts:44` captures `document.activeElement` at
  mount and `:82` calls `.focus()` on it at unmount. For these two overlays the captured
  element is the menu item, which the menu unmounts at the same moment; `.focus()` on a
  detached node is a no-op. The start dialog and the drawer are opened from card buttons that
  stay mounted, which is why they restore correctly.
- **Impact.** WCAG 2.4.3 (Focus Order) on two of the four overlays. Keyboard-only and
  screen-reader users lose their place; nothing is broken for mouse users.

### 3. Field errors in the Add-workspace dialog go stale

- **Symptom.** After a rejected submit, correcting the offending field leaves `aria-invalid="true"`
  and the old `role=alert` message in place. A screen reader keeps announcing an error about a
  value that is no longer there.
- **Repro.** Open Add workspace…, type `not-an-epic-key!` in Epic key, submit, then replace it
  with `DOC-3556`.
- **Expected.** The invalid state clears when the field changes.
- **Observed.** `invalid: ["INPUT desc=_r_1_-epic val=DOC-3556"]` with the message still reading
  "epic must be an issue key such as DOC-3807, or a numeric issue id".
- **Impact.** Cosmetic for sighted users; misleading for assistive technology. Cleared only by
  the next submit.

### 4. The Test prefill renders an empty branch when the issue has no worktree

- **Symptom.** `GET …/prefill?playbook=test` for an issue with no registered worktree renders
  `Verify on the current branch  in this worktree (<path>)` — `{{branch}}` is empty and the
  worktree path names a directory that does not exist.
- **Repro.** `curl "http://127.0.0.1:4400/api/workspaces/docs-nextjs/issues/DOC-3809/prefill?playbook=test"`.
- **Expected.** Either the branch that will be resolved, or wording that does not assert one.
- **Observed.** An empty slot with a double space, alongside a correct
  `warnings: ["no worktree is registered for DOC-3809; its branch is resolved when the session
starts"]`. Starting the session is then refused outright.
- **Impact.** The owner sees, and could edit and send, a prompt that names no branch. The
  warning is present, so the damage is confined to a confusing dialog. `evidence/20-prefill-3809.txt`.

### 5. After a server restart, a live session's state does not recover — only its liveness does

- **Symptom.** A session that changed state while the server was down keeps showing the state
  it had when the server died, indefinitely.
- **Repro.** Start a session, stop the server before the session's next hook event, let the
  session finish its turn, restart the server.
- **Expected (requester's clause).** "after restart the session is still listed live and its
  state recovers via reconcile".
- **Observed.** `qc-DOC-3882-implement` came back listed **live** in Working — correct — but
  showing `bootstrapping` while the real session sat at the prompt having replied `READY`. The
  cache countdown was live and ticking on the same card, because status-line payloads keep
  arriving and spec §5.3 says they change no state. Typing one message into the session healed
  it (`UserPromptSubmit` → working → idle).
- **Root cause.** The reconciler (spec §5.5) only answers "does tmux still have this session",
  and there is no other source: the hooks that would have moved the record were POSTed at a
  dead port and are gone. Not a coding mistake — a design gap the spec does not name.
- **Impact.** After any restart, every live session's card can lie until its next turn. On a
  board being triaged by state, that is the one thing the board is for.

### 6. A failed bootstrap gives no reason anywhere in the UI

- **Symptom.** The card and the session header show `failed`; the exit code and any output are
  nowhere in the browser.
- **Repro.** Set a repo's `bootstrap` to a command that exits non-zero, restart, start a session
  on an issue with no worktree.
- **Expected.** The reason visible where the state is.
- **Observed.** `bootstrap-failed {"exitCode":1}` is in `events.jsonl` and the failed shell is
  left open in tmux for inspection (spec §5.5, working as designed), but the UI shows the word
  `failed` and nothing else — no exit code, no last line of output, no pointer to the tmux
  session. `evidence/24-failed-card.png`.
- **Impact.** The owner must attach to tmux or read `events.jsonl` to learn why a start failed.

### 7. Rewriting the config is not round-trip-clean, and an inline connector can never be removed

- **Symptom.** Adding a workspace and then removing it leaves the config file materially
  changed.
- **Repro.** Note the file, add a workspace from the dialog (creating a new inline issue source),
  remove it again, diff.
- **Expected (requester's clause).** "the config file after removal equals the file before adding".
- **Observed** (`evidence/11-config-diff.txt`), three distinct changes:
  1. **Reformatted.** Every inline array in the owner's hand-written file is expanded one
     element per line — `editor.args`, `runner.models`, `primaryFor`, `reviewStatuses`.
  2. **Defaults materialised.** `docs-nextjs-migration`, which carried neither, gained
     `"reviewStatuses": ["Ready for review"]` and `"pollSeconds": 120`.
  3. **Orphan connector.** The inline connector created from the dialog (`probe-source`) stays
     in `connectors` after its only workspace is deleted, **and there is no UI control and no
     API route to remove a connector** — spec §11 offers workspace create/delete only.
- **Impact.** (1) and (2) are semantically harmless and spec §4 admits the file is rewritten
  wholesale ("`~` is expanded while parsing and is not restored"), but they still rewrite a file
  the owner maintains by hand. (3) is a real one-way door: every mistyped inline connector is
  permanent until the file is edited by hand, and each one logs two warnings on every boot.

## Notes, not defects

1. **`permission mode: default` still does not mean "ask me"**, and `manual` does not gate
   everything. `manual` did **not** prompt for `echo probe` inside the worktree; it **did**
   prompt for a `touch` outside it. The dashboard passes the flag correctly
   (`--permission-mode manual` is in the generated `run.sh`); what is gated is Claude Code's
   decision. Confirmed by experiment.
2. **A forged hook POST moves a live session's state.** `curl -X POST …/api/hooks/<id>/UserPromptSubmit`
   with any JSON object returned 204 and moved the record to `working`. Spec §8.2 states the
   endpoint is unauthenticated and loopback-only; this is the documented posture, recorded here
   because it is the kind of thing a reader will otherwise discover as a surprise.
3. **A killed run records `exitCode: null`** — accepted and documented; confirmed
   (`runs: [{kind:"start", exitCode:null}]` after a kill).
4. **An idle session with no pending shows no second line on its card** — the accepted known
   gap; confirmed. The card reads `Implement · your turn · 56s · ⏳ 59:00` and stops there.
5. **Two workspaces may carry the same display name.** "Docs · Next.js" slugs to `docs-next-js`,
   which does not collide with the existing hand-written id `docs-nextjs`, so the second one is
   accepted. The switcher then shows two identically-named entries distinguished only by their
   epic key — which spec §12 does put there as secondary text. Correct per spec, confusing in use.
6. **`POST …/sessions` is a long synchronous request.** It holds the connection through
   `git fetch`, `git worktree add` and `tmux new-session`, serialised per repo by the mutex.
   Under contention one start took over two minutes to return. No progress is reported until it
   does.
7. **The dashboard has no guardrail on concurrency.** Five sessions started within a few minutes,
   each running `npm ci` and then a full `claude` process, drove this machine into swap (load
   average 92, 7.4 GB of 8 GB swap used) and the **tmux server was OOM-killed**, taking every
   session with it. The dashboard behaved correctly throughout — the reconciler marked all five
   records `exited`/`failed` and the server stayed up — but nothing in the product warns that
   one click costs a `claude` process and an `npm ci`.
8. **`tmux send-keys` was used as the input path in exactly two places**, both labelled in the
   table: moving the selection in the permission dialog to "No", and racing an Escape onto a
   live turn. Everywhere else keystrokes went through the browser's xterm. The reason is Note 9's
   sibling: a plain `click` on `.xterm-screen` to focus the terminal is delivered to the TUI as
   a mouse event and can activate the highlighted option of an open Claude Code dialog — twice
   it approved the permission prompt that was meant to be denied.
9. **A full-page navigation away from a session view leaves the pty attached.** After
   `location.href = …` from one session view to another, `tmux list-clients` still showed the
   previous session attached, and server-side sockets accumulated (1 → 3 → 4 → 6). Closing the
   browser dropped every socket and every tmux client instantly, and an in-app "Back to board"
   never leaked, so the server's teardown is correct and the retention is on the Chromium side.
   Reported as an observation, not a defect, because the root cause could not be pinned to the
   product; a user pressing F5 on a session view would meet the same thing.
10. **In dev mode the API server on 4400 serves a shell that cannot run.** `webRoot` resolves to
    `src/web`, which exists, so `GET http://127.0.0.1:4400/` returns the 770-byte source
    `index.html` referencing `/src/main.tsx`. The board is only usable on 5173 in dev. Harmless
    if you follow the README, confusing if you do not.
11. **The unknown-session view claims the session runs in the main checkout.** `/session/xyz`
    renders "This session runs in the main checkout." and an enabled Kill button for a session
    that does not exist. Cosmetic.
12. **A 2 MB hook body answers 400, not 413**, and the cap is 1 MB.
13. **Requested WS rows are off by one in the pane**: `?rows=30` yields `pane_height 29`, because

## Handover

The MVP is in good shape and the fix commits `0a3b1df..f186925` did what they claimed: one
events socket, a session view that settles, keyboard-reachable overlays, honest actions, the
server-side risk list, and a guard of last resort that this run leaned on harder than intended
when the machine ran out of memory and every session died at once.

What to pick up first:

1. **Bug 1** is a one-line string mismatch that disables a documented escape hatch entirely.
   Either put `--force` in `DirtyWorktreeError`'s message or, better, give `ErrorResponse` a
   machine-readable code instead of matching on prose.
2. **Bug 5** is the one worth a design decision rather than a patch: after a restart the board
   can display a state that is minutes stale, and the board's whole purpose is state. Options
   range from marking a reconciled record as "state unknown" to reading the session's
   `transcript_path`, which the hooks already hand over on every payload.
3. **Bug 2** is four lines in `useFocusTrap`: keep the trigger, not `document.activeElement`, or
   fall back to a caller-supplied element when the saved node is no longer connected.
4. **Bug 7 item 3** — an inline connector with no way out — will bite the first person who
   mistypes an env-var name in the dialog.

Two things a human should confirm before acting on this report:

- **Bug 5 and Bug 6 are gaps against the requester's phrasing, not against `docs/spec.md`.**
  The spec never promises state recovery on reconcile, and never says the failure reason is
  shown. Whoever owns the spec should decide whether the spec or the behaviour is wrong.
- **The permission-denial and Escape-mid-turn results reproduce `docs/spec.md` §5.3's own
  predictions.** They are recorded as confirmed behaviour, not as new defects, but they leave
  the board wrong indefinitely after a user action that the owner will perform often, and that
